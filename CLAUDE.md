## Железные правила
1. Если в исходных данных есть URL — триплеты извлекаются РЕВЕРСОМ реальных
   страниц, а не из общего знания. Нарушение делает всю работу недействительной.
2. Маркетплейсы (Ozon, WB, Яндекс.Маркет) исключать из анализа для инфо-запросов.
3. Каждый значимый триплет внедряется трижды: текст + Schema.org + внешний источник.
   **Исходящие ссылки на авторитетный первоисточник — граница по назначению статьи:**
   - **ON-SITE (свои страницы)** — значимый **нормативный / статистический** факт подкрепляется
     **исходящей ссылкой на первоисточник** (регулятор · офиц. реестр · текст закона · отраслевой
     стандарт): dofollow, в теле при первом упоминании; где применимо — дублируется в JSON-LD
     (`citation` / `isBasedOn`). Источники — из `data/authorities.md` (ведёт niche-expert), только
     реальные и подтверждённые; нет URL — «нет данных», не выдумывать. Это сигнал E-E-A-T/GEO.
   - **OFF-SITE (внешние размещения на чужих площадках)** — authoritative-ссылки НЕ ставим: политику
     ссылок диктует TOS площадки, а цель размещения — бэклинк на наш сайт (см. off-site-ветку).
4. Разметка совпадает с видимым текстом слово в слово.
5. Таблицы — HTML <table>. НИКОГДА не картинкой.
6. Значения-заглушки помечать явно. Числа датировать.
7. Ни один текст не выдаётся без двух проверок: GIST-аудит по III-6 (вердикт на
   каждый блок, тест заменимости, тест первой трети, FAQ-фильтр, проверка точек
   отказа) и техчек гомоглифов по III-6а. Обе обязательны.
8. Ничего не выдумывать. Нет данных — писать «нет данных», а не правдоподобное.
9. **Разметка — НЕ фактор ранжирования и НЕ KPI.** Яндекс не ранжирует по Schema.org напрямую;
   Google почти не даёт FAQ-rich на коммерции; self-serving AggregateRating звёзд в органике не даёт.
   «Получить rich-сниппет» целью/порогом не ставить — цель разметки — машиночитаемость и извлекаемость.
   Свойство вешать только на свой тип (`instrument`→Action, `warranty`→Offer, бренд-`sameAs`→внутри
   `brand`, не на организации). Полностью — `docs/schema-org-cheatsheet.md`.
10. **Governance рискованных заявлений.** Заявление, непроверяемое по прочитанным страницам или
    `input/company.md` (наличие оборудования, «дешевле дилера / до N%», срок гарантии, «ТО не у дилера
    сохраняет гарантию», спорное гео), НЕ подаётся как факт: статус `to-check → confirmed → publish`,
    колонки «подтверждено клиентом» / «риск» в матрице. До подтверждения правовые/гарантийные заявления —
    условной формулировкой. Маркирует triplet-collector, проверяет gist-auditor.

## GIST-логика (слой отбора) — применять всегда

Поверх ранжирования работает отбор в ограниченный набор: SERP — 10 мест,
AI-выдача — 3-5 источников. Отбор балансирует полезность набора и его
разнообразие. Следствие: документ, близкий к уже выбранному более сильному
источнику, имеет добавочную полезность около нуля и вытесняется — даже будучи
качественным.

Как это ложится на триплеты:
- ОБЯЗАТЕЛЬНЫЙ (≥70% доменов) = ядро полезности. Без него страница не попадёт
  в кластер кандидатов. Ядро СОХРАНЯЕМ, но СЖИМАЕМ — отличимости оно не даёт.
- ОТСТРОЙКА (≤34%) = вклад в разнообразие. Именно она выигрывает место.

Практические правила:
1. Ядро — компактно и вверху, не даём ему доминировать по объёму.
2. Главный дифференциатор — в первой трети страницы, не после 5 экранов.
3. Тест заменимости: можно ли заменить страницу лидером топа без потери пользы?
   Да — пересборка, а не правка.
4. Отстройку генерируем в том числе предикатами «точки отказа»: не работает при /
   не подходит для / цена ошибки / перестаёт работать после. Эти узлы редко
   покрыты конкурентами и почти не дублируемы.
5. Симметрия внутри своего кластера — самосозданный конфликтный радиус,
   см. правило незаменимого узла III-7.

ГРАНИЦА ПРИМЕНЕНИЯ (критично): на коммерческих посадочных Яндекса давление
разнообразия слабее. Шаблонные блоки — прайс-таблица, гарантия, NAP, кузова,
FAQPage-разметка — это коммерческие факторы Яндекса. Резать их как «повтор
лидеров» ЗАПРЕЩЕНО. GIST-логика на коммерции применяется к дифференцирующим
блокам и к архитектуре кластера, но не к обязательному ядру.

СТАТУС ФАКТОВ: GIST (Fahrbach et al., NeurIPS 2025, arXiv:2405.18754) — алгоритм
отбора обучающих данных, не ранжирования. «Google внедрил GIST в поиск» и
«потолок выдачи 56%» — непроверенные гипотезы SEO-каналов. Механику используем,
легенду в клиентские документы НЕ пишем.

## Источники правды
- input/serp/ — БОГАТЫЕ выгрузки SERP от оператора: pass-1 + pass-2, колонки
  `Группа | Запрос | ПС | Блок | № | Текст | URL/Источники` (Блок ∈ Топ / Обзор ИИ / Похожий вопрос /
  Похожий запрос / Подсказка). serp-prep делает EXPAND (расширение фраз) по pass-1; финальную
  кластеризацию + парсинг блоков + brand-presence делает serp-parser по обеим выгрузкам.
  Запасной вход (быстрый прогон без serp-prep): простой `Фраза ; URL ; позиция` без колонки Кластер →
  сразу serp-parser (parse_serp.py, режим no-Кластер).
- input/company.md — карточка бизнеса (owned-данные): sameAs, цены, лицензии, персоны, незаменимые узлы; статусы полей verified|marketing|to-check
- input/backlinks.md — бэклинки от оператора для OFF-SITE: колонки «целевой URL · анкор» (ссылки follow). Читает external-tz-writer, вшивает external-copywriter, проверяет external-gist-auditor
- input/prompts.md — PROMPT-SET (опц.): ключи + ИИ-промпты, по которым нас должны находить/цитировать. Вход ТАРГЕТИНГА, НЕ текст для вставки. Заполняет оператор; serp-parser сводит его с наблюдаемыми промптами → data/prompts.md
- data/prompts.md — рабочий prompt-set: операторские (input/prompts.md) + наблюдаемые из блоков «Обзор ИИ / Похожий вопрос» промпты, помечены источником и кластером. Таргетят: tz-writer (citation-target), placement-strategist, external-tz-writer; проверяют gist-auditor (6а) и external-gist-auditor
- input/brand.md (+ assets/brand/) — ДИЗАЙН-СИСТЕМА проекта (опц., на старте): палитра hex, шрифты, логотип, тон. Читают hero-maker (в промпт-бриф обложки) и layout-скилл (CSS-токены). Пусто → нейтральный стиль
- data/serp-parsed.md — кластеры + топ-20 URL, дубли доменов удалены
- data/competitors.md — домены-конкуренты (тот же продукт) → идут в реверс
- data/placements.md — площадки-цели GEO (агрегаторы, листиклы, отзовики, каталоги, СМИ, форумы) → НЕ реверсим; переиспользуется GEO-мониторингом
- data/citation-gaps.md — РОУТЕР двух рычагов: по каждому gap-кластеру (ранжируемся, но AI-обзор не цитирует) маршрут on-site/off-site/оба + кто цитирует. Строит domain-inventory
- data/entities.md — карта сущностей + Wikidata Q + sameAs (sameAs своего бренда — из input/company.md)
- data/interlinks.md — карта семантических КОКОНОВ (силосов) + граф внутренних ссылок ON-SITE: коконы (тематические кластеры страниц), pillar↔дети, sibling-мосты, канонический анкор на цель (один анкор = одна цель). Владелец tz-writer, целостность проверяет cluster-inspector, разводит page-builder
- data/authorities.md — реестр АВТОРИТЕТНЫХ ПЕРВОИСТОЧНИКОВ ниши для ON-SITE-ссылок (правило 3): норма/факт → регулятор/реестр/закон/стандарт → URL → статус (verified/to-check). Ведёт niche-expert; назначает в ТЗ tz-writer, ставит ссылку copywriter, дублирует в citation/isBasedOn schema-markup, проверяет gist-auditor (6б). Off-site такие ссылки не несёт
- data/triplets.md — МАТРИЦА: частотность X/Y, ОБЯЗ/ОТСТРОЙКА, флаг незаменимого узла, тег источника own/competitor

- data/comparison-NN.md — срез «конкурент × атрибут» для статей-сравнений (опционально, comparison-builder)

## Два рычага GEO (on-site + off-site) — читать
Один сигнal citation-gap кормит ОБА рычага, делить по тому, ГДЕ может жить цитата (см. data/citation-gaps.md):
- **on-site** (свои страницы) — AI цитирует брендовые страницы → делаем свою цитируемой (citation target в ТЗ,
  извлекаемый факт + атрибуция). Ветка tripl-tz/write/ship.
- **off-site** (чужие площадки) — AI цитирует только третьи стороны → размещаемся у них. Ветка placement-strategist →
  external-tz-writer → external-copywriter → external-gist-auditor → external/; правила площадки — скилл external-<platform>
  (pluggable). Один проект, один сбор, две писательские ветки по маршруту gap.
- **GEO-петля (geo-monitor) — ⛔ ЗАГЛУШЕНА.** Пост-отгрузочный замер закрытия citation-gap (цитируется ли
  бренд в AI-обзоре «было vs стало») сейчас **не автоматизирован**: агент `geo-monitor` отключён, команда
  `/tripl-ext-monitor` помечена отключённой. Открытые разрывы оператор отслеживает вручную. Включить обратно —
  снять баннер ЗАГЛУШЕН в `.claude/agents/geo-monitor.md` и пометки здесь и в ORCHESTRATION.md/команде.

## Технические заметки
- CSV: кодировка utf-8-sig, разделитель ';'
- При ошибке чтения файла (OSError) — повторить попытку
- Страницы топа качает tools/fetch_pages.py в cache/pages/ (реестр index.json).
  Реверс идёт по кэшу, а не по живым запросам: матрица описывает снимок с датой.
  Читать <md5>.clean.html (документ без скриптов и стилей), оригинал <md5>.html рядом.
- JSON-LD конкурентов в кэше СОХРАНЁН: скрипт вырезает все script-теги, кроме
  ld+json. Разметку извлекать напрямую и помечать как прочитанную, а не косвенный
  вывод. Прежнее правило «script-теги срезаются, выводы по og-тегам» действовало
  для WebFetch и отменено.
- WebFetch на страницы топа — только для доменов из списка «подозрение
  на JS-рендеринг» в отчёте загрузчика.
- Техчек гомоглифов: python tools/homoglyph_check.py <путь>

## Пайплайн (порядок запуска агентов)

```
0    serp-prep (EXPAND: расширение фраз по pass-1) → ⛔ВОРОТА (что дозагрузить); оператор фетчит pass-2
1    serp-parser (парс богатых выгрузок pass-1+pass-2 + кластеризация по выдаче + brand-presence)
1.5  domain-inventory (competitors + placements) → ⛔ВОРОТА-1 (подтверждение scope ДО реверса)
2    ‖ entity-mapper (ест company.md), triplet-collector (own + competitor; реверс только competitors)
2.5  triplet-collector --merge
2.6  niche-expert (режим 1 — базовый скилл ниши) → ⛔ВОРОТА-2 (матрица)
3    niche-expert (режим 2 — обогащение скилла)
4    tz-writer (написание ТЗ)
5    ‖ copywriter × N
6    ‖ gist-auditor × N        ← петля на 5, до 3 итераций
7    cluster-inspector          ← петля на 4 или 2а
8    ‖ schema-markup (разметка + JSON матрицы), infographic-maker (инфографика), hero-maker (бриф hero + og:image)
9    page-builder (стадии 1-2: вёрстка → UX/impeccable)
10   final-inspector            ← петля на ответственных, до 2 итераций
11   page-builder (стадия 3: упаковка в delivery/)  ← только при статусе RELEASE
12   homoglyph-checker          ← финальный техчек, видит preview/ И delivery/
```

‖ — параллельный запуск. Разделение ролей исполнитель/контролёр — жёсткое:
- niche-expert — дважды: режим 1 (базовый, по serp-parsed.md) и режим 2 (обогащение по матрице).
- tz-writer — один режим: пишет ТЗ и проектирует незаменимый узел в каждое (шаг 4). Собственную
  нарезку на дублирование НЕ проверяет.
- cluster-inspector (шаг 7) — ОТДЕЛЬНЫЙ агент, свежий взгляд: проверяет готовую серию на
  каннибализацию (III-7). Петля 7 архитектурная: вердикт «дублирующий массив» возвращается
  в tz-writer (пересборка ТЗ) или entity-mapper, НЕ копирайтеру. Автор ТЗ не ставит себе диагноз.
- page-builder — стадии 1-2 (шаг 9) до финальной инспекции, стадия 3 «упаковка» (шаг 11) —
  только после статуса RELEASE.
- homoglyph-checker (шаг 12) — ОТДЕЛЬНЫЙ агент ПОСЛЕ page-builder целиком: видит финал, включая
  упаковку (delivery/), — чего техчек внутри page-builder не увидел бы.

## Распределение моделей

Критерий: проверяем ли выход агента. Если результат можно проверить
автоматически (JSON валиден / скрипт нашёл или не нашёл) — дешёвая модель
безопасна, деградация видна сразу. Если проверить можно только повторив
работу — нужна сильная модель, потому что слабая не падает, а тихо
штампует «готово».

opus — суждение, где ошибка обнаружится поздно и дорого:
  serp-prep (расширение семантики + классификация интентов — качество непроверяемо, ловится поздно)
  serp-parser (кластеризация по выдаче + разбор блоков + brand-presence — кластеры проверяются только пересбором)
  triplet-collector (нормализация триплетов + карта подтем — ломает всю частотность ниже)
  tz-writer (архитектура страницы: проектирует незаменимый узел в каждое ТЗ)
  copywriter (это продукт)
  gist-auditor (ворота качества текста, выход непроверяем)
  cluster-inspector (тест симметрии серии III-7 — отдельный свежий взгляд, не автор ТЗ)
  final-inspector (сквозная сверка)
  niche-expert (синтез ЦА, запускается раз на проект)
  comparison-builder (опц.: срез «конкурент × атрибут», честные мульти-рейтинги — суждение)
  placement-strategist (off-site: карта размещений клайм×площадка — стратегия, выход непроверяем)
  external-tz-writer (off-site: ТЗ под чужую площадку — архитектура засева цитаты)
  external-copywriter (off-site: текст под площадку — это продукт)
  external-gist-auditor (off-site: ворота качества + TOS/цитируемость, выход непроверяем)

sonnet — работа по чёткой процедуре с проверяемым результатом:
  entity-mapper, domain-inventory,
  schema-markup (разметка + JSON матрицы), infographic-maker (инфографика),
  hero-maker (промпт-бриф на hero + og:image для внешней генерации человеком),
  page-builder (вёрстка + UX-полировка + упаковка),
  geo-monitor (⛔ ЗАГЛУШЕН — отключён; при включении: sonnet, перепроверка brand-presence по gap-кластерам)

haiku — механика с автопроверкой по скрипту:
  homoglyph-checker (техчек по homoglyph_check.py — падение видно сразу; запускается
  последним, после page-builder, видит финал включая упаковку в delivery/).
Доктрина «выход валидируется скриптом → дешёвая модель»: homoglyph-checker падает на
homoglyph_check.py немедленно, деградация модели видна сразу — haiku безопасен.
JSON-валидация матрицы влита подзадачей в schema-markup (sonnet): он внутри себя гоняет
json.load и видит падение сразу.

Оркестратор (основная сессия) — opus: он маршрутизирует и управляет циклами.

Понижать модель можно только после того, как агент отработал на реальном
проекте и качество оказалось избыточным. Заранее не угадывать.
