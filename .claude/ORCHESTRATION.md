# tripl — инструкция оркестрации

Этот файл описывает, как запускать пайплайн tripl после переделки, обсуждённой
в ходе проектирования.

**Как это работает по ролям:**
- **Владелец** запускает 4 команды-блока и проверяет результат на воротах между
  ними. Это ВСЁ ручное участие: 4 запуска + 3 плановых взгляда. Владелец НЕ
  запускает агентов по одному.
- **Claude** внутри каждого блока сам оркеструет агентов: порядок, параллельные
  запуски, ожидание, проверка файлов, переход между этапами. Оркестратор внутри
  блока — это Claude, не человек.

```
владелец: /tripl-collect  →  Claude сам гонит этапы 1-3  →  ⛔ владелец смотрит матрицу
владелец: /tripl-tz       →  Claude сам гонит этап 4     →  ⛔ владелец смотрит структуру
владелец: /tripl-write    →  Claude сам гонит этапы 5-7  →  ⛔ владелец читает тексты
владелец: /tripl-ship     →  Claude сам гонит этапы 8-15 →  готово
```

Итого: **4 запуска + 3 взгляда** на плановых воротах. Плюс изредка — реакция на
внеплановую ⛔-остановку ВНУТРИ блока, если данные оказались плохими (см. ниже):
Claude замирает посреди блока и ждёт решения, потому что продолжать автоматически
было бы вредно.

Файл для двух адресатов:
- **Claude** — что автоматически исполняется внутри каждого блока;
- **владелец** — что проверяется на воротах между блоками.

> **Статус:** файл фиксирует ЦЕЛЕВОЕ состояние. Часть компонентов ещё не
> реализована — см. раздел 0 «Готовность». Не запускать по инструкции, которая
> опережает факт: сначала закрыть раздел 0, потом прогонять.

## 0. Готовность — проверить до первого прогона

Пайплайн не стартует, пока не закрыты все пункты. Проверь каждый:

- [ ] **fetch_pages.py существует** — загрузчик страниц топа в кэш. Без него
      triplet-collector встанет на первом кластере (он читает кэш, не веб).
- [ ] **page-finisher собран** — объединение html-renderer + schema-markup +
      ux-reviewer + cms-packager в один агент. Если агенты ещё раздельные —
      либо слить, либо в блоке /tripl-ship запускать их по очереди.
- [ ] **hero-maker в промпт-версии** — выдаёт бриф на картинку, не рисует SVG.
- [ ] **модели проставлены** — 13 на claude-opus-4-8, json-builder и
      homoglyph-checker на haiku.
- [ ] **4 команды созданы** в .claude/commands/: tripl-collect, tripl-tz,
      tripl-write, tripl-ship.
- [ ] **CLAUDE.md на месте**, первой строкой метка `# НИША: <название>`.
- [ ] **выгрузка топа** в input/.
- [ ] **прокси настроены** (если нужны) в tools/fetch_config.json.

## 1. Модель запуска: 4 блока с воротами, не один автомат

Полный автомат на 15 этапов теряет управляемость при падении в середине.
Ручной запуск 15 агентов — мучение. Решение: **автоблоки с ручными воротами**.

```
/tripl-collect  → сбор данных (этапы 1-3)      ⛔ СТОП: смотришь матрицу
/tripl-tz       → проектирование (этап 4)      ⛔ СТОП: утверждаешь структуру
/tripl-write    → тексты и контроль (этапы 5-7) ⛔ СТОП: читаешь тексты
/tripl-ship     → оформление и сдача (8-15)     → delivery/ + брифы hero
```

Ворота стоят там, где ошибка дорого стоит:
- плохая матрица испортит ВСЕ тексты → смотрим до текстов;
- плохая структура даст каннибализацию → смотрим до написания;
- слабые тексты дешевле переписать до оформления → смотрим до вёрстки.

Внутри блока агенты идут сами. Между блоками решаешь ты. Каждый блок можно
перезапустить с середины по журналу (раздел 6).

**Два типа остановок — не путать:**
- **Плановые ворота** (⛔ в конце блока) — штатная точка. Блок доработал, показал
  результат, ждёт твоего «дальше». Их ровно 3, они предсказуемы.
- **Внеплановые остановки** (⛔ внутри блока) — срабатывают, когда данные плохие
  и продолжать вредно: покрытие парсинга <50%, ноль незаменимых узлов, «слишком
  слабо» дважды по странице, «дублирующий массив». Блок НЕ доходит до конца сам —
  замирает посреди и спрашивает. Это не сбой, а защита: автопродолжение
  обесценило бы работу или сдало брак.

## 2. Общие правила ведения (для Claude внутри любого блока)

1. **Журнал прогона.** В начале создать/дополнить `review/run-log.md`. После
   каждого этапа — строка: этап, агент(ы), статус, ключевые числа из отчёта,
   время. При падении журнал — единственный способ понять, откуда перезапускать.
2. **Параллельные запуски — одним сообщением.** Все Task-вызовы блока в одном
   сообщении, иначе теряется параллельность.
3. **Проверка выходов.** После каждого этапа убедиться, что файлы реально
   созданы. Нет файла — не идти дальше, разобраться.
4. **Падение агента.** Упал или вернул пустое — один повтор. Упал снова —
   остановиться, показать его вывод. НЕ подменять работу агента своей.
5. **Лимиты API (важно, была реальная проблема).** 529 Overloaded и session
   limit убивают агента целиком, внутреннего повтора нет. Поэтому:
   - тяжёлые параллельные агенты — ВОЛНАМИ, не залпом;
   - triplet-collector: по 2-3 экземпляра;
   - copywriter: по 5-6 экземпляров;
   - при 529/лимите у экземпляра: пауза 60 сек, удалить его недописанный файл,
     один перезапуск.
6. **Лимиты циклов.** Переписывание после аудита — макс 3. Финальные правки —
   макс 2. Превышение → остановка и вопрос владельцу.

## 3. БЛОК 1 — /tripl-collect (этапы 1-3, ДВОЕ ворот)

Собирает всё сырьё: топ, кэш страниц, сущности, активы, матрицу, скилл ниши.
**Ворот теперь двое:** дешёвая проверка scope ДО дорогого реверса (ВОРОТА-1) и
прежняя проверка матрицы (ВОРОТА-2).

```
00 serp-prep (EXPAND)  пред-шаг ВНЕ блока: по pass-1 расширяет фразы → output/to-parse.txt
   ⛔ ВОРОТА serp-prep: что дозагрузить; оператор фетчит pass-2 в input/serp/
01 serp-parser         (парс богатых выгрузок pass-1+pass-2 + кластеризация по выдаче + brand-presence)
03 domain-inventory   → data/competitors.md + data/placements.md
⛔ ВОРОТА-1 (новые, дешёвые): карта кластеров + ядро конкурентов + площадки; scope до реверса
[02 entity-mapper (ест company.md)  ∥  04 triplet-collector (competitor + own)]
merge (тег own/competitor)
05 niche-expert
⛔ ВОРОТА-2 (прежние): матрица → решить, идти на /tripl-tz
```

**Почему domain-inventory переехал ДО реверса:** именно он делит домены на
конкурентов (реверсим) и площадки (не реверсим), поэтому решает, что вообще
качать и разбирать. Дешёвую проверку scope делаем до дорогого triplet-collector.

### Пред-шаг — serp-prep (opus), режим EXPAND
Запускает оператор ДО /tripl-collect: по pass-1 расширяет семантику → `output/to-parse.txt` +
`data/expand-report.md` → ⛔ворота → оператор фетчит одобренные фразы как pass-2. serp-prep
кластеризацию НЕ финализирует и `serp-ready.md` НЕ собирает (это делает serp-parser).

### Предусловия
Обе выгрузки (pass-1 + pass-2) в `input/serp/` есть? `input/company.md` заполнен? CLAUDE.md прочитан?
Нет pass-2 → сначала прогнать serp-prep (EXPAND). Пусто → ⛔ запросить.

### Этап 1 — serp-parser (opus)
`input/serp/*` (богатые выгрузки pass-1+pass-2) → `data/serp-parsed.md`. Агент сливает обе выгрузки,
разбирает блоки (Топ→чистые URL; Обзор ИИ→домены из «Текст», не из `goto?url=`; Похожий/Подсказка→
метаданные), **кластеризует по выдаче ВНУТРИ агента** (фразы с ≥K общих URL в топ-10, старт K=3) и
считает brand-presence (органика + citation-gap в AI-обзоре). Запасной вход: простой `Фраза;URL;позиция`
без Кластера → parse_serp.py, режим no-Кластер.
Проверить: файл создан, есть число кластеров, K, разброс Y.
Пары кластеров с пересечением ≥70% — выписать в run-log (нужны на этапах 4 и 7).
Фразы вне кластеров и спорные — придержать для ВОРОТ-1.
⛔ Y<7 где-то → пометить: частотность ненадёжна.

### Этап 1.5 — domain-inventory (первый проход: классификация доменов)
`data/serp-parsed.md` → **`data/competitors.md` + `data/placements.md`** (плюс его
обычные выходы `data/domain-assets.md`, `data/client-questions.md`).
Каждый домен топа: **competitor** (тот же продукт → реверсим) / **placement**
(агрегатор, листикл, отзовик, каталог, Я.Бизнес/Карты, СМИ, форум → цель GEO,
не реверсим) / **`?`** (спорный, решает оператор). `placements.md` переиспользуется
GEO-мониторингом.

### ⛔ ВОРОТА-1 — владелец подтверждает scope ДО реверса (новые, дешёвые):
Показать: карту кластеров (с K), ядро конкурентов (`competitors.md`), список
площадок-целей (`placements.md`), спорные домены `?` и фразы вне кластеров.
Решения оператора:
- **scope:** все кластеры / только топ-N по частотности;
- **правка спорных:** этот домен — competitor или placement?
Дальше дорогой реверс идёт ТОЛЬКО по подтверждённым competitor-доменам.

### Этап 2.0 — fetch_pages.py (скрипт, не агент)
После ВОРОТ-1, только по доменам-конкурентам:
`python tools/fetch_pages.py --input data/serp-parsed.md` (competitor-домены из
`data/competitors.md`) → `cache/pages/`. Площадки не качаем.
Разобрать отчёт:
- ⛔ покрытие <50% по кластеру → показать упавшие URL, спросить: продолжать ли
  (можно догрузить `--retry-failed` и пересобрать затронутые кластеры);
- список JS-доменов из отчёта — придержать, передать сборщикам на этапе 2.

### Этап 2 — параллельный блок сбора (после ВОРОТ-1)
ОДНИМ сообщением:
- entity-mapper (opus) — **читает `input/company.md`** (sameAs своего бренда) →
  `data/entities.md`
- niche-expert режим 1 (opus) → `.claude/skills/project-<slug>/SKILL.md`
- triplet-collector (opus) — **по экземпляру на кластер**, волнами по 2-3, каждому
  номер его кластера и список JS-доменов. Два источника: **competitor** (реверс
  `competitors.md`) + **own** (`input/company.md`) → `data/triplets-part-NN.md`
- (comparison-builder — опционально, только для comparison-кластеров «Топ-N»,
  запускается ПОСЛЕ merge по `data/triplets.md` + `input/company.md` →
  `data/comparison-NN.md`; в сеть не ходит)

Дождаться всех. Проверить наличие всех файлов.

### Этап 2.5 — слияние матрицы
triplet-collector с параметром `merge` → `data/triplets.md` + `data/predicates.md`.
В матрице — **тег источника `own` / `competitor`** и флаг незаменимого узла.
Проверить: сколько частей слито, сколько предикатов схлопнуто.
⛔ ноль незаменимых узлов по серийным кластерам → остановиться, показать.
В тексты без узлов идти бессмысленно (III-7).

### Этап 3 — niche-expert режим 2 (opus)
+`triplets.md`, `domain-assets.md` → обогащение скилла: точки отказа, конфликты
фактов, сверка словаря с фактурой топа.

### ⛔ ВОРОТА-2 БЛОКА 1 — владелец проверяет матрицу:
- матрица: адекватны ли ОБЯЗ/ОТСТРОЙКА, не выдумана ли частотность; теги
  own/competitor проставлены;
- карта подтем: есть ли пустоты (места для отстройки);
- незаменимые узлы: есть ли они, по каким сущностям;
- вопросы клиенту: что надо запросить до текстов.
Матрица плохая → чинить здесь, не идти в ТЗ.

## 4. БЛОК 2 — /tripl-tz (этап 4)

### Этап 4 — tz-writer (opus)
`triplets.md` + `entities.md` + `domain-assets.md` + скилл ниши →
`data/tz/tz-NN.md` + `data/external-tasks.md`.
Проверить: файлы ТЗ созданы, есть таблица «кластер → tz-NN».

⛔ **ВОРОТА:** блокеры (страницы без узла, без YMYL-подписанта) — показать
списком. СПРОСИТЬ владельца: писать все страницы или только без блокеров?
После ответа — если появился slug, дописать в шапку copywriter.md поле
`skills: project-<slug>`.

### ⛔ ВОРОТА БЛОКА 2 — владелец проверяет:
- структура: не копирует ли каркас топа, есть ли дифференциатор в первой трети;
- нарезка: кластеры со слиянием (пересечение ≥70%) разведены правильно;
- блокеры: решено, что делать с каждым.
Структура плохая → чинить ТЗ (или вернуть в entity-mapper), не идти в тексты.

## 5. БЛОК 3 — /tripl-write (этапы 5-7)

### Этап 5 — copywriter (opus), параллельно
По экземпляру на ТЗ из утверждённого списка, волнами по 5-6. Каждому: путь к ТЗ
+ путь к `drafts/page-NN.md`. Внутри каждого — humanizer + сверка с ТЗ +
гомоглиф-чек за собой.

### Этап 6 — аудит и переписывание ⟳ (макс 3)
6.1. gist-auditor (opus) параллельно на каждый текст → `review/audit-NN.md`.
6.2. Собрать статусы:
     - «готово к публикации» → выход из цикла;
     - «мелкие правки» / «нужна итерация» / «слишком слабо» → в переписывание.
6.3. Параллельно copywriter только по забракованным (каждому его audit-NN.md) →
     снова gist-auditor по ним же.
6.4. Макс 3 круга. ⛔ «слишком слабо» дважды по одной странице → вынуть,
     показать (проблема в ТЗ/данных, не в тексте). После 3 кругов остались
     непринятые → остановиться, показать список.

### Этап 7 — cluster-inspector (opus)
→ `review/cluster-report.md`.
- «состоятельна» → дальше;
- «точечные дыры» → выполнить рекомендации через адресатов, повтор;
- ⛔ «дублирующий массив» → ОСТАНОВИТЬСЯ, показать. Возврат в архитектуру
  (entity-mapper/tz-writer) — решение владельца, не автоматика: он обесценивает
  часть готовых текстов.

### ⛔ ВОРОТА БЛОКА 3 — владелец читает тексты:
- проходят ли на вкус, не водянистые ли;
- дифференциатор реально в начале;
- заглушки [ТРЕБУЕТСЯ] — собрать, отправить клиенту.
Тексты слабые → переписать до оформления (дешевле, чем после).

## 6. БЛОК 4 — /tripl-ship (этапы 8-15)

### Этап 8 — параллельный блок оформления
ОДНИМ сообщением:
- infographic-maker (opus) → `assets/infographics/*.svg` + placement
- hero-maker (opus) → `assets/hero/page-NN-prompt.md` (БРИФ, не картинка)
- json-builder (haiku) → `data/triplets.json`
(schema-markup теперь ВНУТРИ page-finisher, отдельно не запускать)

### Этапы 9-13 — page-finisher (opus), по странице
`drafts/` + разметка + placement + бриф hero → `preview/page-NN.html` →
`delivery/`. Четыре фазы в одном проходе: разметка → вёрстка → UX → упаковка.
Можно параллельно (файлы не пересекаются), волнами.
- ⛔ заглушка дожила до упаковки → дыра этапа 15, показать, не дочищать самому.

**Между фазами UX и упаковки — /impeccable polish preview/**
Это команда ОСНОВНОЙ СЕССИИ, НЕ передавать сабагенту. После polish —
page-finisher коротким проходом: не сломал ли polish таблицы/контраст/разметку.

### Этап 14 — homoglyph-checker (haiku)
Прогон по drafts/, data/, assets/, preview/. Финальная строка обязана быть
«после проверки чисто». Не чисто → исправить через него же, повтор.

### Этап 15 — final-inspector (opus) ⟳ (макс 2)
→ `review/final-report.md`. RELEASE или FIX.
- FIX → по таблице запустить адресатов (каждому его строки); если тронуты
  тексты — точечно gist-auditor + homoglyph-checker по ним; повтор inspector.
- ⛔ после 2-го FIX → остановиться, показать таблицу.

### Финальная сводка (из run-log)
Страниц сдано/задумано · круги на этапах 6 и 15 · вопросы клиенту (client-questions
+ заглушки + NAP-конфликты одним списком) · внешние задачи (external-tasks) ·
что не проверено и почему · **брифы на hero-картинки** (человек генерит внешне
по assets/hero/page-NN-prompt.md) · пути к delivery/.

## 6б. ВЕТКА OFF-SITE — /tripl-ext-plan → /tripl-ext-write → /tripl-ext-monitor

Один проект, один сбор (БЛОК 1), но ДВЕ писательские ветки — разводит `data/citation-gaps.md`
(строит domain-inventory на этапе 1.5): по каждому gap-кластеру маршрут **on-site / off-site / оба**.

- **on-site** (AI цитирует брендовые страницы) → обычные БЛОКИ 2-4 (/tripl-tz с блоком «citation target» →
  /tripl-write → /tripl-ship). Это внутренний пиар: своя страница становится цитируемой.
- **off-site** (AI цитирует только третьи стороны) → эта ветка. Внешний пиар: размещаемся на чужих площадках,
  чтобы бренд процитировали.

Поток off-site (модели: placement-strategist/external-tz-writer/external-copywriter/external-gist-auditor — opus;
geo-monitor — ⛔ЗАГЛУШЕН; homoglyph-checker — haiku):
```
/tripl-ext-plan   placement-strategist (off-site gaps + placements.md + own-узлы) → data/placement-plan.md
                  ⛔ ВОРОТА: оператор утверждает карту размещений
/tripl-ext-write  external-tz-writer → data/tz-ext/ → external-copywriter (волнами) → external/ (md+html) →
                  external-gist-auditor (петля ≤3) → homoglyph-checker
                  ⚠ правила площадки берутся из скилла external-<platform> (pluggable, задаёт владелец);
```

## 7. Куда возвращается работа при FIX

| Симптом | Ответственный агент |
|---|---|
| Текст неполон, разметка требует чего нет в тексте | copywriter |
| Разметка своевольничает при полном тексте | page-finisher (schema-фаза) |
| Архитектурная симметрия, дублирующий массив | tz-writer / entity-mapper |
| Развалилась сборка: таблицы, JSON-LD, мета | page-finisher |
| Слепая инфографика, контраст, мобильный | page-finisher (ux-фаза) |
| Смешение алфавитов, невидимые символы | homoglyph-checker |
| Дубли/пропажи в JSON | json-builder |

Правило: архитектурные проблемы НЕ адресуются копирайтеру — переписывание текста
не лечит симметрию и дыры плана.

## 8. Что переделано относительно первой версии

Сводка изменений, зафиксированных этой инструкцией:

1. **Один /tripl → четыре команды-ворота.** Управляемость вместо слепого автомата.
2. **Парсинг вынесен в Python-скрипт.** fetch_pages.py качает в кэш, triplet-collector
   читает локальные файлы. Причина: длинный агент × opus × параллель выбивал лимиты
   API. Скрипт снимает сетевые вызовы из контекста и даёт кэш для перезапуска.
3. **18 агентов → 15.** page-finisher = html-renderer + schema-markup + ux-reviewer
   + cms-packager (работали по одному HTML подряд без ворот между ними).
   Проверяющих и сборщиков НЕ объединяли.
4. **hero-maker: генерация → промпт-бриф.** Картинку генерит человек внешне
   (ChatGPT/DALL·E). og:image только растр, не SVG.
5. **Модели: 13 opus-4-8 + 2 haiku.** haiku у json-builder и homoglyph-checker —
   там выход валидируется автоматически, opus не нужен и рискует самодеятельностью.
6. **Гомоглиф-чек в трёх точках.** Вход (serp-parser), производство (агенты за
   собой), выход (homoglyph-checker последним — видит JSON-LD и SVG, рождённые
   после копирайтера).
7. **Карта подтем H2/H3** добавлена в triplet-collector — диагностика покрытия
   и пустот, НЕ шаблон структуры.
8. **Проекты по папкам.** Одна ниша = одна папка = запуск оттуда. Шаблон +
   клоны, общее через git/add-dir.

## 9. Режим 300+ тем — отдельная ветка (не по этой инструкции)

Эта инструкция — для 8-50 страниц. На 300 темах / 50k URL порядок другой:
парсинг на сервере промышленным скриптом; каннибализация решается ДО текстов
на графе пересечений (cluster-architect); перелинковка вычисляется из графа
в конце (linkage-planner); тексты пишутся партиями по супер-узлам.
Подробности — в PIPELINE.md, раздел 8. По этой инструкции 300 тем НЕ гонять.
