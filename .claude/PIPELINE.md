# tripl — карта проекта

Единый обзор пайплайна: агенты, порядок, петли, точки остановки, масштабирование.
Держи этот файл в корне проекта и перечитывай перед прогоном, пока последовательность не в голове.

---

## 1. Что это

Конвейер из агентов Claude Code, который превращает выгрузку поискового топа
в готовые к публикации SEO-тексты по методике **tripl** (триплеты + GIST-логика).

Ключевой принцип методики: триплеты не придумываются из общего знания,
а **извлекаются реверсом реальных страниц топа** с подсчётом частотности.
Обязательное ядро (что есть у всех) обеспечивает попадание в выдачу;
отстройка (чего нет у конкурентов) выигрывает место.

---

## 2. Организация проектов

**Одна ниша = одна папка = запуск Claude Code из неё.** Проекты изолированы:
свой CLAUDE.md, свои агенты, свой кэш, своя история. Разные ниши в одной папке
недопустимы — перемешаются данные.

```
~/claude/
├── tripl-template/     эталон: агенты, команды, методичка, скрипты. Без данных.
├── tripl-ddd/          рабочая ниша (клон шаблона + данные)
├── tripl-kitai/        рабочая ниша
└── _shared/            (позже) общая методичка + скрипты, через --add-dir
```

Новая ниша — клон шаблона: `cp -R tripl-template tripl-<slug>`.
Первой строкой каждого CLAUDE.md — метка `# НИША: <название>`, чтобы не путать проекты.
При старте сессии — `/status`, проверить рабочую папку.

## 3. Состав: 15 агентов + графовые надстройки

Модели: **opus** — суждение, где ошибка обнаружится поздно и дорого;
**sonnet** — работа по чёткой процедуре с проверяемым результатом;
**haiku** — механика, выход валидируется автоматически.

| # | Агент | Модель | Роль |
|---|---|---|---|
| — | *(скрипт)* fetch_pages.py | — | Загрузка страниц топа в кэш |
| 1 | serp-parser | sonnet | Парсинг выгрузки, кластеры, Y, пересечения доменов |
| 2 | entity-mapper | sonnet | Карта сущностей ниши, Wikidata, sameAs, структура URL |
| 3 | domain-inventory | sonnet | Активы клиента, NAP, вопросы клиенту |
| 4 | triplet-collector | opus | Реверс топа → матрица + карта подтем H2/H3; режим merge |
| 5 | niche-expert | opus | Исследование ЦА и языка ниши → скилл (2 режима) |
| 6 | tz-writer | opus | Матрица → проверяемые ТЗ по страницам |
| 7 | copywriter | opus | Тексты по ТЗ (+ humanizer, + скилл ниши) |
| 8 | gist-auditor | opus | GIST-аудит, петля переписывания |
| 9 | cluster-inspector | opus | Проверка серии на каннибализацию (III-7) |
| 10 | infographic-maker | sonnet | SVG-инфографика по данным |
| 11 | hero-maker | sonnet | Промпт-бриф на hero-картинку (генерит человек внешне) |
| 12 | json-builder | haiku | Матрица → triplets.json |
| 13 | page-finisher | sonnet | Разметка + вёрстка + UX + чистка + упаковка (4-в-1) |
| 14 | homoglyph-checker | haiku | Техчек гомоглифов, последним из правящих |
| 15 | final-inspector | opus | Сквозная финальная сверка, RELEASE/FIX |

**page-finisher** = объединение html-renderer + schema-markup + ux-reviewer +
cms-packager. Работают последовательно по одной странице, без твоих ворот между
шагами — логично слить в один проход.

**Что НЕ объединяли:** проверяющих (gist-auditor, cluster-inspector,
homoglyph-checker, final-inspector) — свежий взгляд контролёра нельзя мешать
с исполнением; сборщиков (entity-mapper, domain-inventory, triplet-collector) —
идут параллельно, слияние убьёт параллельность.

## 4. Порядок прогона

Легенда: ‖ параллельный блок · ⟳ петля с лимитом · ⛔ остановка и решение владельца

```
0.   Предусловия: выгрузка в input/, CLAUDE.md прочитан, режим выбран, run-log создан

1.   serp-parser ................ input/*.csv → serp-parsed.md
     ⛔ Y<7 где-то → частотность ненадёжна

2.0  fetch_pages.py (скрипт) .... serp-parsed.md → cache/pages/
     ⛔ покрытие <50% по кластеру → продолжать ли

2.   ‖ entity-mapper · domain-inventory · niche-expert(р1) ·
       triplet-collector × кластеры (волнами по 2-3)
     → entities.md, domain-assets.md, скилл, triplets-part-NN.md

2.5  triplet-collector --merge .. → triplets.md + predicates.md
     ⛔ ВОРОТА: ноль незаменимых узлов по серийным → стоп

3.   niche-expert(р2) ........... обогащение скилла: точки отказа, конфликты фактов

4.   tz-writer .................. → data/tz/tz-NN.md
     ⛔ блокеры (нет узла / нет YMYL-подписанта) → писать все или чистые?

5.   ‖ copywriter × ТЗ (волнами по 5-6) → drafts/page-NN.md

6.   ⟳ (макс 3): ‖ gist-auditor → переписывание забракованных → повтор
     ⛔ «слишком слабо» дважды по странице → проблема в ТЗ/данных

7.   cluster-inspector ......... → cluster-report.md
     ⛔ «дублирующий массив» → возврат в архитектуру (твоё решение)

8.   ‖ infographic-maker · hero-maker · json-builder
     (schema-markup теперь внутри page-finisher)

9-13 page-finisher × страницы .. разметка+вёрстка+UX+чистка+упаковка
     → preview/, delivery/
     10a. /impeccable polish — команда СЕССИИ, не агента
     10b. page-finisher коротким проходом: polish не сломал?

14.  homoglyph-checker ......... финальная строка «после проверки чисто»

15.  ⟳ (макс 2): final-inspector → RELEASE / FIX
     FIX → адресаты из таблицы → повтор
     ⛔ 2-й FIX → стоп, показать таблицу

СВОДКА: страниц сдано, итерации, вопросы клиенту, внешние задачи, что не проверено
```

## 5. Запуск: 4 команды с воротами, не один автомат

Полный автомат на 15 этапов теряет управляемость при падении в середине.
Ручной запуск 15 агентов — мучение. Середина — автоблоки с ручными воротами:

```
/tripl-collect  → этапы 1-3   СТОП: смотришь матрицу
/tripl-tz       → этап 4      СТОП: утверждаешь структуру и блокеры
/tripl-write    → этапы 5-7   СТОП: читаешь тексты
/tripl-ship     → этапы 8-15  готово в delivery/ + брифы на hero
```

Ворота стоят там, где ошибка дорого стоит: плохая матрица испортит все тексты →
смотрим до текстов; плохая структура даст каннибализацию → смотрим до написания.

**Журнал прогона** review/run-log.md — после каждого этапа строка со статусом
и числами. При падении — единственный способ понять, откуда перезапускать.

## 6. Куда возвращается работа при FIX

| Симптом | Ответственный агент |
|---|---|
| Текст неполон, разметка требует чего нет в тексте | copywriter |
| Разметка своевольничает при полном тексте | page-finisher (schema-часть) |
| Архитектурная симметрия, дублирующий массив | tz-writer / entity-mapper |
| Развалилась сборка: таблицы, JSON-LD, мета | page-finisher |
| Слепая инфографика, контраст, мобильный | page-finisher (ux-часть) |
| Смешение алфавитов, невидимые символы | homoglyph-checker |
| Дубли/пропажи в JSON | json-builder |

Правило: архитектурные проблемы НЕ адресуются копирайтеру — переписывание
текста не лечит симметрию и дыры плана.

## 7. Три источника гомоглифов — три точки проверки

Гомоглиф (латинская буква в русском слове) невидим глазу и ломает машинное
чтение и склейку сущностей в разметке. Заводится на разных этапах, поэтому
одной проверки мало:

- **вход** — serp-parser чистит выгрузку (этап 1)
- **производство** — copywriter, infographic-maker, hero-maker, page-finisher
  прогоняют `tools/homoglyph_check.py` за собой (ловят своё раннее заражение)
- **выход** — homoglyph-checker проверяет ВСЁ последним (этап 14), включая
  JSON-LD, мета, SVG-подписи — слой, который рождается после копирайтера
  и где гомоглиф наиболее вреден: проходит валидатор, но не склеивается с графом

## 8. Масштаб 300+ тем / 50 000 URL — отдельный режим

Малый пайплайн (8-50 страниц) на таком объёме не работает. Три изменения:

**Парсинг** выносится на сервер: fetch_pages.py промышленного уровня —
очередь, устойчивость к перезапуску, дедупликация страниц (один агрегатор
сидит в сотнях кластеров, качать раз). Дни автономной работы, вне модели.

**Каннибализация решается ДО текстов, на графе.** Матрица пересечений доменов
от serp-parser становится фундаментом. Новые компоненты:
- `tools/cluster_graph.py` — граф кластеров, группы с пересечением ≥70% → супер-узлы
- агент `cluster-architect` (opus) — интерпретирует граф в структуру сайта:
  что слить, что pillar+дочерние, что самостоятельно. 300 тем → ~90 pillar + дочерние.
  Каннибализация исключена архитектурно: дубли по доменам не станут двумя страницами.

**Перелинковка вычисляется из графа, не пишется руками.** Агент `linkage-planner`
(после всех ТЗ) строит план перелинковки как обход графа с правилами:
дочерняя→pillar, pillar→дочерние, pillar→смежные, инфо→коммерция 2-4.
Контроль: нет изолированных, нет переспама, анкоры не дублируются.

**Поток вместо разового прогона:**
```
Фаза 0 (вне модели): парсинг 50k URL в кэш. Дни.
Фаза 1 (раз): граф → cluster-architect → структура. ВСЯ каннибализация тут.
Фаза 2 (партиями по супер-узлам): сбор→ТЗ→тексты→аудит, 5-15 страниц за партию.
Фаза 3 (раз, в конце): linkage-planner сшивает партии в силос.
```
Каннибализация — глобально в фазе 1 (партии должны знать друг о друге).
Перелинковка — глобально в конце (когда все страницы существуют).
Нужен трекинг прогресса по темам — иначе на сотой партии не вспомнишь состояние.

## 9. Внешние инструменты

- **fetch_pages.py** — загрузка топа. Прокси в tools/fetch_config.json (в .gitignore).
- **homoglyph_check.py** — техчек. Whitelist, ключи --strict / --fix / --all.
- **impeccable** — полировка вёрстки. `/impeccable polish` — команда сессии.
  Устанавливается `npx impeccable install`, настройка `/impeccable init` → PRODUCT.md.
- **hero-картинки** — генерит человек по брифу от hero-maker во внешнем инструменте
  (ChatGPT/DALL·E). Пайплайн выдаёт промпт, не картинку. og:image только растр,
  не SVG (соцсети SVG в превью не рендерят).

## 10. Железные правила (из CLAUDE.md)

1. Есть URL → триплеты реверсом реальных страниц, не из общего знания.
2. Маркетплейсы (Ozon, WB, Маркет, Авито) исключать для инфо-запросов.
3. Каждый значимый триплет — трижды: текст + Schema.org + внешний источник. Значимый норматив/статфакт
   на ON-SITE-странице — с исходящей ссылкой на первоисточник (data/authorities.md; dofollow; опц.
   citation/isBasedOn). OFF-SITE authoritative-ссылки не ставим (там политику задаёт площадка).
4. Разметка = видимый текст слово в слово.
5. Таблицы — HTML `<table>`, никогда картинкой.
6. Заглушки помечать явно. Числа датировать.
7. Текст не выдаётся без GIST-аудита и техчека гомоглифов.
8. Ничего не выдумывать. Нет данных → «нет данных».
9. Топ-20, пороги от Y: обязательный ≥70%, отстройка ≤34%.

GIST-логика: обязательное ядро сжимать (не даёт отличимости), отстройку —
в первую треть. Граница: на коммерции Яндекса ядро (прайс, гарантия, NAP,
FAQPage) не резать — это коммерческие факторы, а не «повтор лидеров».
