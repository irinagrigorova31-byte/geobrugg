Выполни пайплайн tripl. Аргументы: $ARGUMENTS

# Предусловия — проверить до запуска

1. В input/ лежит выгрузка топа (CSV/XLSX). Пусто — остановись и запроси файл.
   Демо-данные не подставлять.
2. Прочитай CLAUDE.md. Все решения по ходу пайплайна — по нему.
3. Если режим не указан в аргументах — спроси у пользователя одним вопросом:
   полный цикл / только матрица (этапы 1-3) / только тексты (этапы 4-7, требует
   готовой матрицы) / только сдача (этапы 8-13, требует готовых текстов).

# Правила ведения пайплайна

- ЖУРНАЛ ПРОГОНА: создай review/run-log.md. После каждого этапа дописывай строку:
  этап, агент(ы), статус, ключевые числа из отчёта, время. При падении любого
  агента журнал — единственный способ понять, откуда перезапускать.
- Параллельные запуски: все Task-вызовы параллельного блока — В ОДНОМ сообщении.
- После каждого этапа проверяй, что выходные файлы реально созданы. Файла нет —
  не иди дальше, разберись.
- Агент упал или вернул пустой результат — один повтор. Упал снова — остановись
  и покажи мне его вывод. Не подменяй работу агента своей.
- Лимиты циклов из CLAUDE.md соблюдаются жёстко: 3 итерации переписывания,
  2 финальные правки. Превышение — остановка и вопрос мне.
- triplet-collector волнами по 2 экземпляра, не по 6. При 529 или session
  limit — пауза 60 сек, один перезапуск экземпляра.
- НЕДОПИСАННЫЕ ФАЙЛЫ НЕ УДАЛЯТЬ. Инкрементальная запись — главная защита от
  сбоев: она уже спасла 3 кластера из 3. Порядок действий с частичным
  triplets-part-NN.md: посмотреть хвост файла. Обрыв на середине строки
  таблицы — обрезать битую строку. Файл заканчивается целой порцией —
  оставить как есть и передать следующему экземпляру: «дочитай домены
  с такого-то, допиши в существующий файл, пересчитай частотность на полный
  знаменатель Y». Пересобирать с нуля то, что уже прочитано, запрещено.

# ЭТАП 1. Парсинг выгрузки
Запусти serp-parser. Проверь: data/serp-parsed.md создан, в отчёте есть число
кластеров и разброс Y. Пары кластеров с пересечением ≥70% — выпиши в run-log:
они понадобятся на этапах 3 и 7.

# ЭТАП 2. Сбор (параллельный блок)

2.0. python tools/fetch_pages.py --input data/serp-parsed.md --report cache/pages/fetch-report.txt
     Запускать в фоне (run_in_background) или по кластерам --cluster NN:
     при вежливой паузе 2-4 сек на домен полная выгрузка не укладывается
     в 10-минутный лимит Bash. Флаг --report сам пишет отчёт в файл
     (кросс-платформенно, без shell-tee) — из него берётся список JS-доменов.
     Кластеры с покрытием <50% — покажи мне, спроси, продолжать ли.
     Список JS-доменов из отчёта передай сборщикам при запуске.

ОДНИМ сообщением запусти:
- entity-mapper
- domain-inventory
- niche-expert (режим 1)
- triplet-collector — по одному экземпляру НА КАЖДЫЙ кластер из data/serp-parsed.md,
  каждому передай номер его кластера. При >6 кластеров запускай волнами по 5-6
  экземпляров, дожидаясь завершения волны.
Дождись всех. Проверь: data/entities.md, data/domain-assets.md,
data/client-questions.md, .claude/skills/project-<slug>/SKILL.md,
data/triplets-part-NN.md на каждый кластер.

# ЭТАП 2.5. Слияние матрицы
Запусти triplet-collector с параметром merge. Проверь: data/triplets.md создан,
в отчёте — сколько частей слито и сколько предикатов схлопнуто.
ВОРОТА: если в отчёте merge ноль незаменимых узлов по серийным кластерам —
остановись и покажи мне. Идти в тексты без узлов бессмысленно (III-7).

# ЭТАП 3. Обогащение скилла ниши
Запусти niche-expert (режим 2). Проверь по его отчёту, сколько гипотез
подтверждено/опровергнуто.

# ЭТАП 4. ТЗ
Запусти tz-writer. Проверь: файлы в data/tz/ созданы, в отчёте есть таблица
«кластер → tz-NN». Блокеры из отчёта (страницы без узла, без подписанта YMYL) —
в run-log и покажи мне списком. СПРОСИ: писать все страницы или только без блокеров?
После ответа — если появился slug проекта, допиши в шапку copywriter.md
в поле skills: project-<slug>.

# ЭТАПЫ 5-6 ИДУТ ВОЛНАМИ ПО 2 СТРАНИЦЫ
Волна = 2 страницы, проходящие путь «текст → аудит → правки» до конца.
Следующая пара берётся только после того, как предыдущая закрыта.
Одновременно в работе не больше 2-3 агентов — это защита от 529 и лимита сессии,
а не пожелание. Пары формируй по родству тем: соседние страницы пишутся
с общим контекстом и их проще проверить на симметрию.

# ЭТАП 5. Тексты (волна: 2 экземпляра)
По одному copywriter на каждое ТЗ текущей пары, оба Task одним сообщением.
Каждому передай: путь к его ТЗ и путь к выходному файлу drafts/page-NN.md.

# ЭТАП 6. Аудит и цикл переписывания (в пределах текущей волны)
6.1. По одному gist-auditor на каждый текст ПАРЫ, оба одним сообщением.
     Каждому передай путь к тексту.
6.2. Собери статусы из review/audit-NN.md.
     «готово к публикации» → страница выходит из цикла.
     «готово после мелких правок» / «нужна итерация» → в список переписывания.
     «слишком слабо» → тоже в список, но пометь в run-log.
6.3. Для списка переписывания: параллельно copywriter только для этих страниц
     (каждому — путь к его audit-NN.md), затем снова gist-auditor для них же.
6.4. Максимум 3 круга. «Слишком слабо» два раза подряд по одной странице —
     вынь её из цикла и покажи мне: проблема в ТЗ или данных, не в тексте.
     После 3-го круга остались непринятые — остановись, покажи список со статусами.
6.5. Пара закрыта, когда оба текста имеют статус «готово к публикации».
     Запиши волну в run-log (какие страницы, сколько кругов) и бери следующую
     пару — возвращайся к этапу 5. Все пары пройдены — иди на этап 7.

# ЭТАП 7. Инспекция кластера
Запускается ТОЛЬКО когда все страницы прошли аудит — на двух страницах тест
симметрии бессмыслен, он про серию целиком.
Запусти cluster-inspector (ОТДЕЛЬНЫЙ агент, свежий взгляд — не автор ТЗ).
Вердикт «архитектура состоятельна» → дальше.
Вердикт «точечные дыры» → выполни его рекомендации через указанных в отчёте
агентов, затем повторный cluster-inspector.
Вердикт «дублирующий массив» → ОСТАНОВИСЬ и покажи мне отчёт. Возврат в
архитектуру (tz-writer / entity-mapper) — моё решение, не автоматика: он
обесценивает часть готовых текстов.

# ЭТАП 8. Оформление (параллельный блок)
ОДНИМ сообщением: schema-markup (разметка страниц + JSON матрицы),
infographic-maker (инфографика), hero-maker (промпт-бриф на hero + og:image).
Проверь: разметка в drafts/ под H2 `## РАЗМЕТКА`, placement-файлы при наличии SVG,
брифы hero (assets/hero/page-NN-prompt.md), data/triplets.json валиден.
Hero/og:image — ручной шаг ВНЕ пайплайна: человек генерит картинки по брифам и
кладёт PNG по путям из брифов; page-builder знает путь og заранее из брифа.

# ЭТАП 9. Сборка (page-builder, стадии 1-2)
Запусти page-builder по каждой странице (можно параллельно — файлы не пересекаются).
Стадии: вёрстка HTML (забирает разметку из блока `## РАЗМЕТКА` в head) → UX-полировка
(/impeccable). Техчек гомоглифов здесь НЕ делается — он отдельным агентом после упаковки.
Проверь: preview/page-NN.html на каждую страницу; расхождения «разметка ↔ текст»
из отчёта — в run-log, при наличии закрой через schema-markup или copywriter
(по адресату), потом дальше. Стадию упаковки здесь НЕ запускать — она после инспекции.

# ЭТАП 10. Финальная инспекция
Запусти final-inspector.
RELEASE → этап 11.
FIX → по таблице из review/final-report.md запусти указанных агентов (каждому
передай его строки таблицы), затем: если правки коснулись текстов — точечно
gist-auditor по затронутым страницам; затем повторный final-inspector.
Максимум 2 круга. После 2-го FIX — остановись, покажи таблицу.

# ЭТАП 11. Упаковка (page-builder, стадия 3)
Запусти page-builder в режиме упаковки — ТОЛЬКО при статусе RELEASE.
Остановился из-за заглушек [ТРЕБУЕТСЯ] — это дыра 10-го этапа: покажи мне,
НЕ пытайся дочистить сам.
Проверь: delivery/ содержит page-NN.html и instructions на каждую страницу.

# ЭТАП 12. Техчек гомоглифов (финальный, после упаковки)
Запусти homoglyph-checker — ОТДЕЛЬНЫЙ агент ПОСЛЕ page-builder целиком.
Прогон по preview/ И delivery/ (он видит финал, включая то, что внесла упаковка).
Финальная строка review/homoglyph-report.md обязана быть «после проверки чисто».
Не чиста — разберись по отчёту, исправь через него же, повтори. Без неё не выдавать.

# ФИНАЛЬНАЯ СВОДКА
Из review/run-log.md собери и покажи:
- страниц сдано / всего задумано;
- итерации: сколько кругов на этапах 6 (аудит) и 10 (финальная инспекция);
- вопросы клиенту: сведи data/client-questions.md + заглушки + неразрешённые
  NAP-конфликты в один список;
- задачи внешнего слоя: сослись на data/external-tasks.md с числом задач;
- что не проверено и почему (из отчёта final-inspector);
- пути к delivery/.
