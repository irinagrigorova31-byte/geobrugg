Выполни БЛОК 1 пайплайна tripl — сбор данных. Аргументы: $ARGUMENTS

Ты оркеструешь агентов внутри этого блока сам: порядок, параллельные запуски,
ожидание, проверка файлов. Владелец запустил одну команду и ждёт результат
на воротах в конце. НЕ проси его запускать агентов по одному.

# Предусловия
1. Прочитай CLAUDE.md — все решения по нему.
2. В input/serp/ лежат ОБЕ богатые выгрузки — pass-1 и pass-2 (колонки
   `Группа | Запрос | ПС | Блок | № | Текст | URL/Источники`)? Их даёт оператор ПОСЛЕ
   пред-шага serp-prep (EXPAND по pass-1 → список фраз на дозагрузку → оператор фетчит
   pass-2). Если pass-2 ещё нет — сначала прогони агента serp-prep (режим EXPAND) и
   останови на его воротах; демо не подставлять.
   input/company.md заполнен (карточка бизнеса: sameAs, цены, лицензии, персоны)?
   Пусто → ОСТАНОВИСЬ, запроси файлы.
   (Запасной вход без serp-prep: простой `Фраза ; URL ; позиция` без Кластера → serp-parser читает его через parse_serp.py.)
3. Создай/дополни review/run-log.md. После каждого этапа — строка: этап, агент,
   статус, ключевые числа, время.

# Правила ведения (соблюдать весь блок)
- Параллельные Task-вызовы — В ОДНОМ сообщении.
- После каждого этапа проверяй, что выходные файлы созданы. Нет файла — разберись,
  не иди дальше.
- Агент упал/пустой результат — один повтор. Упал снова — остановись, покажи вывод.
- Лимиты API (была реальная проблема: 529, session limit убивают агента целиком):
  triplet-collector запускай ВОЛНАМИ по 2-3 экземпляра, не залпом. При 529/лимите
  у экземпляра — пауза 60 сек, удали его недописанный triplets-part-NN.md, один
  перезапуск.

Блок идёт через ДВОЕ ворот: ВОРОТА-1 (дешёвые, scope до реверса) и ВОРОТА-2
(прежние, матрица). Порядок:
serp-parser → domain-inventory (competitors+placements) → ⛔ВОРОТА-1 →
[entity-mapper ∥ triplet-collector] → merge → niche-expert → ⛔ВОРОТА-2.

# ЭТАП 0 (пред-шаг, вне этого блока) — serp-prep, режим EXPAND
serp-prep запускает ОПЕРАТОР до /tripl-collect: по pass-1 расширяет семантику и выдаёт
`output/to-parse.txt` (что дозагрузить) → ворота → оператор фетчит pass-2 в input/serp/.
serp-prep НЕ кластеризует и serp-ready.md НЕ собирает. К моменту /tripl-collect обе выгрузки на месте.

# ЭТАП 1 — serp-parser (парс богатых выгрузок + кластеризация по выдаче + brand-presence)
Запусти serp-parser. Вход input/serp/ (pass-1 + pass-2, богатый формат), выход data/serp-parsed.md.
Агент сливает обе выгрузки, разбирает блоки (Топ → чистые URL; Обзор ИИ → домены ИЗ «Текст», не из
`goto?url=`-мусора; Похожий/Подсказка → метаданные), строит кластеры сам по пересечению выдачи
(фразы с ≥K общих URL в топ-10, старт K=3) и считает brand-presence (органика + citation-gap в AI-обзоре).
Проверь: файл создан, в отчёте число кластеров, K и разброс Y.
Пары кластеров с пересечением доменов ≥70% — выпиши в run-log (нужны на этапах 4 и 7).
Фразы вне кластеров и спорные — придержи для ВОРОТ-1.
Y<7 в каком-то кластере — пометь в run-log: частотность ненадёжна.

# ЭТАП 1.5 — domain-inventory (классификация доменов ДО реверса)
Запусти domain-inventory. Вход data/serp-parsed.md.
Выход: data/competitors.md + data/placements.md (плюс обычные data/domain-assets.md,
data/client-questions.md). Каждый домен топа: competitor (тот же продукт → реверсим)
/ placement (агрегатор, листикл, отзовик, каталог, Я.Бизнес/Карты, СМИ, форум →
цель GEO, не реверсим) / ? (спорный). placements.md переиспользуется GEO-мониторингом.

# ⛔ ВОРОТА-1 — подтверждение scope ДО дорогого реверса (новые, дешёвые)
Покажи владельцу и ОСТАНОВИСЬ:
- карту кластеров (с K);
- ядро конкурентов (data/competitors.md);
- список площадок-целей (data/placements.md);
- спорные домены ? и фразы вне кластеров.
Спроси решения: scope (все кластеры / только топ-N по частотности) и правку
спорных (competitor или placement?). Дорогой реверс дальше идёт ТОЛЬКО по
подтверждённым competitor-доменам.

# ЭТАП 2.0 — загрузка страниц (скрипт, после ВОРОТ-1)
Качаем ТОЛЬКО домены-конкуренты из data/competitors.md. Площадки не качаем.
Выполни: python tools/fetch_pages.py --input data/serp-parsed.md
Разбери отчёт:
- Покрытие <50% доменов по какому-то кластеру → ОСТАНОВИСЬ, покажи владельцу
  список упавших URL, спроси: продолжать ли (можно догрузить --retry-failed
  и пересобрать затронутые кластеры).
- Список JS-доменов из отчёта — сохрани, передашь сборщикам на этапе 2.
Если скрипта нет или сеть недоступна — ОСТАНОВИСЬ и скажи: без кэша
triplet-collector встанет, нужен загрузчик.

# ЭТАП 2 — параллельный блок сбора (после ВОРОТ-1)
ОДНИМ сообщением запусти:
- entity-mapper → data/entities.md (ЧИТАЕТ input/company.md — sameAs своего бренда)
- niche-expert (режим 1) → .claude/skills/project-<slug>/SKILL.md
- triplet-collector — ПО ЭКЗЕМПЛЯРУ НА КАЖДЫЙ кластер, волнами по 2-3. Каждому
  передай номер его кластера и список JS-доменов. Два источника: competitor
  (реверс data/competitors.md) + own (input/company.md). Площадки НЕ реверсить.
  Выход — data/triplets-part-NN.md на кластер.

Дождись всех. Проверь наличие всех файлов.

# ЭТАП 2.5 — слияние матрицы
Запусти triplet-collector с параметром merge.
Выход: data/triplets.md + data/predicates.md. В матрице — тег источника
own/competitor и флаг незаменимого узла.
Проверь: сколько частей слито, сколько предикатов схлопнуто.
ВОРОТА-СТОП: если в отчёте merge ноль незаменимых узлов по серийным кластерам —
ОСТАНОВИСЬ, покажи владельцу. В тексты без узлов идти бессмысленно (III-7).
(Опционально: для comparison-кластеров «Топ-N» запусти comparison-builder по
data/triplets.md + input/company.md → data/comparison-NN.md.)

подтверждено/опровергнуто.
